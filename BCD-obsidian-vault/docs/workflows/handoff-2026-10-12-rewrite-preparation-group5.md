## 3. Важный контекст и ограничения

### Уже принятые группы 1–2 и reboot: не согласовывать заново

- Документированная шкала255 по умолчанию **плюс требование OEM совместимости**
  с нестандартными шкалами. Reflection Legacy имеет историческое назначение;
  способ выбрать после проверки актуальности обхода, не копировать и не отбрасывать
  механически. Существующий floor5 BCD — raw12 при255; это не физическая гарантия.
- Единая opacity: на Legacy Android12+ дополнительная window alpha влияет
  на видимую силу. Отрицательные presets при миграции сохраняются численно,
  без автоматического пересчёта; однократное краткое сообщение об изменении силы.
- Шаг из Auto берёт актуальный системный raw, а не старую numeric цель.
  При sync=true внешнее изменение ОС снимает overlay/таймер; sync=false не
  отыгрывает системное изменение самовольно. Отличать собственное уведомление записи.
- Обычное первое/повторное открытие BCD не меняет свет и не повторяет команду.
  Допустимое восстановление актуальной сессии при recreation сохраняет исходный
  deadline, не умножает окно; позднее восстановление не оживляет истёкшее затемнение.
  Force-stop не преодолевать. Forced crash restart/alarm+kill удаляется.
- Boot policy: Auto default, Last, fixed5..100 с initial25; восстановление
  overlay в Last опционально/defaultoff и только после первого unlock.
  Исходный timer deadline проходит через reboot без паузы/rearm.
  Недостоверный срок не восстанавливает старое затемнение. Ранняя защита
  при доступной обработке/WRITE поднимает достоверный manual raw<12 до12,
  остальные raw и Auto не меняет; нет гарантии первого кадра.
- При установленном отказе **актуальной boot Auto цели** и доступной manual записи
  одна резервная попытка25/raw63 без overlay, без изменения policy Auto.
  Неизвестный результат не отказ; новая цель отменяет старый резерв; без retry loop.
  Это boot-контракт, не универсальный fallback для любой Auto команды.
- Сохраняются валидные настройки при совместимом обновлении; подпись/fixtures
  ещё нужны. Полный принятый boot-контракт: RULE-041–RULE-048, не алгоритм часов/FGS.

### Группа 3: таймер и аварийное снятие приняты

- Таймер defaultoff, сохранённая длительность3h; выбор30min..24h шаг30min.
  Настройка «включён» и активный отсчёт — разные состояния.
- Каждая новая принятая отрицательная команда, включая повтор того же числа,
  slider и +/- с отрицательным результатом, начинает полный срок заново.
  Повторная доставка той же операции не новая команда и не rearm.
- Save изменённой длительности при активном таймере начинает срок от сохранения;
  unchanged Save, Cancel/Back и простое закрытие не rearm. Отмена не сохраняет выбор.
- Enable при действующей отрицательной сессии начинает полный срок сейчас;
  без затемнения только сохраняет настройку. Disable отменяет срок, сохраняя
  затемнение и длительность. Nonnegative/Auto/external sync отменяют срок,
  не выключая настройку таймера.
- Временное исключение не пауза/rearm таймера. **Принята только эта семантика
  исключений, а не группа 5 целиком.** Истёкшее затемнение не оживлять при возврате.
- Истечение при доступной обработке снимает overlay и запрашивает Auto.
  Таймер non-wakeup/inexact, не требует нового exact-alarm grant, не обещает
  ровную секунду во сне или завершение до первого кадра после пробуждения.
  Запоздавшее отменённое/заменённое событие не меняет новую цель/сессию.
- Четыре полученных SCREEN_ON/OFF с соседними интервалами <=1250ms снимают
  актуальное отрицательное затемнение, отменяют таймер и запрашивают Auto.
  Gap>1250ms начинает последовательность заново. Это не любые четыре нажатия
  за5s и не доказательство физической кнопки/обязательного чередования событий.
- Последним отдельным ответом принят вариант2: **только актуальная отрицательная
  сессия**. Manual25/nonnegative/Auto без неё сохраняются; старый numeric preset
  не доказывает действующую сессию. DEC-017 CHANGE/CONFIRMED_BY_USER.

### Группа 4: все восемь случаев приняты

- Manual/Auto требуют WRITE_SETTINGS, negative дополнительно overlay.
  Просмотр главного экрана/настроек/помощи доступен без этих grants.
  Отказ не закрывает всё BCD; поздний grant сам не выполняет старую команду.
- Missing settings Activity: доступное объяснение/альтернатива без crash/ложного
  success/deferred команды; фоновое событие не открывает permission Activity само.
- Legacy ожидание до10s проверяло запаздывающий canDrawOverlays Android8,
  с проверкой каждую секунду и ранним завершением при true. Не делать10s
  обязательной UI нормой; проверить актуальность наAPI26 до выбора реализации.
- Быстрые кнопки уведомления defaultoff отдельно от обязательного notice
  длительного активного сервиса. Toggle не новая light command и не меняет
  яркость/overlay/deadline. Наличие notice не обещает вечную работу.
- POST_NOTIFICATIONS только33+ по намерению включить controls. Denial сам
  не блокирует manual/Auto/допустимый ОС dimming; честно отразить недоступность
  панели. FGS notice передаётся ОС; его фактическая видимость определяется ОС.
- Стабильный канал управления яркостью: initial HIGH без sound/vibration,
  затем пользовательские настройки сохраняются при toggle/reopen/recreation.
  Приоритет в BCD ведёт в системные настройки канала. Не создавать новый ID
  при запуске и не обходить user importance. FGS type/запуск ещё не выбран.
- Убрать отдельный запрос принудительного закрытия системной панели Android
  и его опцию на всех поддерживаемых API. На26–30 это принятый продуктовый выбор;
  на31+ Legacy уже отключает. Не обещать, что ОС всегда оставит панель открытой.
  **Это не опция закрытия собственной панели BCD из ещё не принятого DEC-007.**
- По снимкам Honor требуется читаемое текстовое состояние отдельно от малой
  иконки, цельные подписи с минусом/процентом без обрезки/наложения, различимые
  удобные кнопки. Макет/цвета/размеры ещё не выбраны; не решать только уменьшением
  шрифта. Проверить темы, масштаб, узкую область и оба состояния уведомления.

- Русский язык, короткие содержательные обновления во время работы.

  короткие списки, ключевое жирным. Названия controls смысловые до выбора макета.

  бессмысленным без комментариев, истории и источников; сохранить даже отвергнутый

  Исторические appendices не текущий статус; читать актуальный заголовок/последнюю дату.
- Вопросы обычным текстом, без popup. Не просить повторное разрешение на уже

## 9. Инструменты, команды и проверки

Среда Windows/PowerShell. Cwd нового проекта из таблицы; при работе с материалами
явно задавать их Git root. Для поиска `rg`/`rg --files`, для чтения `Get-Content`
с `-Encoding UTF8`, независимые чтения можно batch. Не запускать параллельные
Gradle builds в одной папке. Для документов Android build не нужен.

Полезные команды в корне материалов:

```powershell
git -c core.fsmonitor=false status --short
git -c core.fsmonitor=false diff --check
git -c core.fsmonitor=false diff --cached --check
rg -n 'DEC-011|DEC-018|DEC-019|DEC-020' BCD-obsidian-vault/docs/specification/behavior-decisions.md
rg -n 'E17|E18|E19|E20|E26|E27|E28|E29' BCD-obsidian-vault/docs/specification/source-evidence.md
```

был стандартный каталог .git/hooks только с .sample; это не обещание для нового чата.
Некоторые Git diff/stage/commit команды в sandbox раньше выдавали ошибку worktree;
точные разрешённые команды выполнялись с require_escalated после auto-review.
Не обходить hooks/проверки; при новом отказе сначала разобраться в причине.

Веб использовался для официальных Android источников P01–P09 и исходных ссылок
Legacy. Новые платформенные утверждения проверять по актуальным первичным источникам;
историческое SO сообщение не считать доказательством текущего OEM поведения.
Не переносить старые утверждения «инструмент недоступен» без новой проверки.
