## 2. Структура приложения и владельцы

Начать с существующего одного Gradle-модуля `:app`. Разделение пакетами:
`ui`, `control`, `platform`, `data`, `commerce`. Не создавать набор пустых
модулей, универсальный framework состояний или DI framework до необходимости.
Составление зависимостей — один явный `AppContainer` с отдельным ранним boot-путём.

| Часть | Ответственность | Чего ей не поручается |
|---|---|---|
| Compose UI | Показывает состояние, отправляет действия пользователя | Прямые записи Settings, WindowManager, rearm из composition/onResume |
| MainViewModel | StateFlow состояния Main; преобразует пользовательские действия в запросы | Владение длительным затемнением или временем жизни service |
| SettingsViewModel и EditorViewModel | Настройки, проверка ввода, черновик, явные Save/Cancel | Автоприменение сохранённого preset |
| ControlCoordinator | Один последовательный владелец принятой цели и переходов; разрешает все эффекты света/сессии | Хранение Activity или ожидание Billing/Ads |
| DimmerService | Android-время жизни negative сессии; notice, регистрация screen/OS observers/detector | Вторая копия продуктовой логики и отдельная цель для виджета |
| OverlayController | Единственный handle собственного окна; add/update/remove на main thread | Создание второго окна при повторной доставке |
| Platform adapters | Settings/readback, grants, alarm, clock, UsageEvents, notification, widget host | Самостоятельные retry/rearm или открытие permission UI из background |
| Repositories | Типизированные модели данных, транзакции, миграция и наблюдение изменений | Неявные световые команды от изменения любого preference |
| Commerce adapters | Play purchase/restore, право, промо-игра, Ads | Блокирование основной команды света сетевым ответом |

Все компоненты работают в одном процессе. Receiver/widget/notification входы
обращаются к тому же координатору, а не создают ViewModel. `Application.onCreate`
не начинает Billing/Ads и не открывает CE до unlock. ViewModel переживает
конфигурационное пересоздание; допустимость восстановления процесса проверяется
координатором отдельно. Сбор данных UI ограничивается видимым lifecycle.

Для реализации MVVM понадобятся прямые зависимости ViewModel/Compose lifecycle
и используемых Coroutines API, если их нет среди прямых зависимостей шаблона.
Предлагается добавить только нужные artifacts в существующем совместимом семействе,
с каталогом и strict checksums, отдельным проверенным изменением будущей реализации.
Сейчас ничего не добавляется и не обновляется. Storage выбран по оценке6.1;
Glance/Hilt/Cucumber и дополнительные модули не следуют из самого MVVM.

## 3. Пять разных видов состояния

| Модель | Поля по смыслу | Владелец и сохранение |
|---|---|---|
| Settings | 8 main и4 shared presets, независимые шаги, visibility, close, controls, sync, timer enabled/duration, exclusions, boot policy | Repository; долговременная запись, валидные значения не заменяются default |
| Requested | Auto либо Numeric(p); origin, commandId, revision; отдельно последняя пользовательская цель для принятой Last policy | Coordinator; durable запись не означает успешного эффекта ОС |
| Observed | Прочитанные mode/raw, достоверность/время чтения; факт собственного окна и его alpha; доступные grants | Platform → coordinator; после запуска повторное чтение, unknown не raw0 |
| Runtime session | sessionId, revision, применяемая negative цель, наличие/приостановка окна, исходный deadline, boot marker, операция в работе/результат | Coordinator + service; сохранённая квитанция проверяется перед recovery |
| UiState / editor draft | Экран, выбранный объект, текст ввода/ошибка, положение прокрутки, сообщения, статус выполнения | ViewModel; SavedStateHandle для небольшого черновика, не для действующего света |

Настройка таймера enabled не равна active deadline; duration не deadline.
Последний preset не равен requested, а requested не observed. Сохранённое
`active=true` не доказывает существование окна после смерти процесса.
Отрицательная сессия может продолжаться с временно снятым окном по исключению.
Отказ создания окна сам по себе не превращается в такую приостановку.

UI получает одну согласованную проекцию: цель, доступный фактический результат,
статус затемнения, срок, разрешения и последнее относящееся сообщение. Например:
«Затемнение −25%» при работающем окне; «Затемнение временно снято» при suspension;
«Цель −25% не применена» при отказе. При sync=false и внешнем изменении ОС
показываются различие цели и системного режима, без обратной записи.
В обычном пользовательском UI нет raw, generation или внутренних BUG ID.

Результат операции — компактная запись: что запрошено, что подтверждено для
mode/raw/окна, полный/частичный отказ либо неподтверждённый результат и причина.
Причины не требуют отдельных машин состояний для каждого вида исключения.

## 4. Команды и эффекты

Reducer здесь — чистая функция перехода состояния от события. Effect — действие
внешнего мира: запись ОС, окно, alarm или сохранение. Эти понятия не добавляют
новые продуктовые режимы.

### 4.1. Общий путь

1. Вход создаёт запрос с источником: user action, system event либо recovery.
   Новый tap получает новый commandId даже при том же p. При системной
   повтордоставке сохраняется ID принятой операции. Идентичность PendingIntent
   не используется как ID каждого нового нажатия.
2. Координатор проверяет диапазон, живой widget instance, текущие grants и
   основание запуска. Для шага из Auto требуется новое чтение raw у действия.
   Неверный ввод/отсутствующий обязательный доступ не принимают световую команду.
3. Для принятой команды сохраняются revision, исходное время принятия и
   deadline, если он нужен. Отдельно сохраняется стадия незавершённого эффекта.
   Повтордоставка использует эту квитанцию и не получает новый now+duration.
4. Один исполнитель выполняет эффекты последовательно. Координатор продолжает
   принимать события, пока внешнее действие ожидает результата. Перед каждым
   новым эффектом проверяются актуальная revision, срок, остановка и grants.
   Уже совершённую запись нельзя отменить корутинной cancellation.
5. Результат/readback возвращается событием. Старый completion не меняет новую
   цель и не разрешает старое addOverlay/reserve. Реальные изменения ОС всё равно
   учитываются наблюдением; нельзя скрыть их как будто старый вызов не случился.
6. Обновляются UiState, notice/widgets. Закрытие Main по close option разрешается
   только успешным относящимся preset/Auto результатом для ещё открытой панели.

Для negative сначала проверить допустимость FGS/notice и opacity, затем получить
подтверждённые manual/raw minimum; только после этого разрешать окно.
Окно одно: opaque black content, alpha в LayoutParams.alpha. Main thread владеет
WindowManager handle, service teardown снимает именно этот handle.
Для Auto/nonnegative сначала сделать старое затемнение и срок недействительными,
снять окно, затем запросить системное состояние. Частичный отказ показывается
как фактический результат; автоматического rollback или retry loop нет.

Если durable запись нового deadline/квитанции не удалась, не создавать новую
восстанавливаемую negative сессию с недоказанным таймером. При уже изменённой
системной настройке сообщать partial, не выдумывать атомарность ОС и storage.
Успешный Save настроек означает подтверждённую транзакцию, а не запуск async apply.

### 4.2. Актуальность и гонки

| Событие | Переход / проверка |
|---|---|
| Новый negative tap, даже−75 на границе | Новая revision; полный срок от принятия при enabled timer |
| Повтор доставки той же операции | Та же цель/исходный deadline; сверка эффекта без второго окна |
| Continuous slider | Только изменившееся целое от user gesture; приём во время движения, не ожидание release; программный refresh не команда |
| Save duration | Сравнить с сохранённой duration в момент транзакции; изменённая при active timer → новый deadline; unchanged/Cancel/Back ничего не переустанавливают |
| Auto/nonnegative / external sync=true | Старая сессия и её expiry недействительны до последующих эффектов |
| Excluded / unknown / grant revoke | Принятые RULE-030–031; unknown не exit, late grant не pending command |
| Expiry / screen protection | Действуют только на актуальную negative сессию; terminal marker до запроса Auto, повтор не пишет ОС второй раз |
| Новый запрос во время boot Auto/reserve | Старая revision не может разрешить reserve или окно |
| Повторный вход/rotation/locale | Только UI/read/reconcile; без нового светового запроса |

Не накапливать неограниченную очередь старых slider positions. Допустимо
заменить ещё не принятый промежуточный position более свежим в той же gesture;
принятые команды, явные taps и deadline не сливать. Правильность continuous
поведения проверить до выбора оптимизации; не вводить произвольную задержку до release.

Own-write echo: вести ожидаемые mode/raw и стадию конкретной записи,
перечитывать согласованную пару, учитывать callbacks обоих ключей и readback.
Не «игнорировать следующий callback». Достоверное отличающееся внешнее состояние
при sync=true выигрывает и блокирует оставшиеся старые эффекты.
ContentObserver не сообщает автора: одновременную внешнюю запись точно того же
значения нельзя отличить по одному callback. Это граница знания, которую нельзя
закрыть fake-маркером; TEST-010/011 проверяют реальные перестановки событий.

## 5. Android runtime, boot и часы

### 5.1. Время жизни и входы

Первый технический кандидат — `specialUse` для продолжающейся
negative сессии, включая временную suspension с обязанностью отслеживать выход,
таймер и защитные события. Отказ от постоянного FGS при Auto/manual (8.6)
не принят: сначала небольшая техническая проверка влияния на привычные surfaces.
Обоснование suspension и магазинный допуск остаются ранней проверкой.
Manifest-кандидат: WRITE_SETTINGS, SYSTEM_ALERT_WINDOW, RECEIVE_BOOT_COMPLETED,
FOREGROUND_SERVICE, FOREGROUND_SERVICE_SPECIAL_USE, POST_NOTIFICATIONS,
PACKAGE_USAGE_STATS; service type/subtype с точным описанием затемнения.
Нет exact-alarm grant, AccessibilityService и общего постоянного wake lock.

| Вход/состояние | Планируемое выполнение |
|---|---|
| Явный negative в видимой Main | Разрешённый старт FGS, обязательный notice, затем эффекты |
| Явный widget/notification tap | Явный проверенный адресат; право фонового старта по этому пользовательскому действию, отказ учитывается |
| Manual/Auto без negative сессии | Короткая команда в живом процессе/ограниченной receiver-обработке; дальнейшее наблюдение и FGS lifetime отдельно проверяются по8.6 |
| Auto/nonnegative завершили negative | Снять окно, отменить deadline/detector/screen receiver; завершение именно dimming работы. Наблюдение/управляющее уведомление и service lifetime остаются предметом8.6 |
| Suspended negative | Service продолжает конкретную действующую работу; без второго окна/нового срока |
| Controls on при Auto/manual | FGS lifetime/актуальность labels ещё проверяются по8.6; обычное уведомление без FGS — кандидат, не принятое ограничение поведения |
| LOCKED_BOOT_COMPLETED | Короткий DE-only guard; Billing/Ads/CE не создавать; overlay запрещён |
| BOOT_COMPLETED после unlock | CE reconcile принятой policy/срока, проверка boot-start выбранного типа; overlay только при всех условиях |
| USER_UNLOCKED | Дополнительный reconcile в уже допустимом runtime; не самостоятельная лицензия на старт FGS |
| Inexact expiry | Короткий explicit receiver; живой владелец завершает сессию, новый FGS для expiry не создаётся |
| Разрешённое ОС пересоздание service | Recovery той же квитанции, не replay нового пользовательского tap |
| Task Manager Stop / force-stop | Не устраивать restart; при последующем входе проверить остановку до recovery/expiry |

У notification content — прямой Activity PendingIntent. Командные кнопки идут
в координатор и не открывают permission Activity из background. Проверить
target37 sender/creator BAL на каждом настоящем пути. При невозможности
фоновой команды результат доступен при открытии BCD; нет скрытой отложенной
команды после выдачи grant. Ограниченная receiver-операция не должна ждать сеть.

### 5.2. Stop, orphan alarm и recreation

Task Manager Stop не присылает cleanup callback; alarms могут пережить процесс.
На API30+ проверяется доступная история ApplicationExitInfo относительно
сохранённой квитанции/времени работы процесса; REASON_USER_REQUESTED завершает
допустимость старого runtime. На API26–29 и при неполной истории сам файл
не разрешает восстановление: нужен относящийся допустимый OS recovery вход.
Обычный Launcher-вход таким доказательством не является.

При установленной пользовательской остановке старый sessionId помечается
terminal, старый alarm отменяется. Поздний expiry не пишет Auto и не создаёт
service: пользовательская остановка уже прекратила эту сессию. Новая команда
пользователя создаёт новый ID. Last user target хранится отдельно от разрешения
продолжить остановленную сессию; stop marker нельзя обойти boot/обычным reopen.

Если alarm пришёл без живого service: сначала stop/boot/квитанция/новая revision,
затем срок. Допустимая доказанная актуальная сессия может быть завершена короткой
операцией Auto без нового FGS; неизвестная допустимость не служит разрешением
скрытой записи. Эта граница особенно проверяется на API26–29: отсутствие
ApplicationExitInfo нельзя объявить доказанной способностью отличить все причины.
Если TEST-035/047 не подтверждают путь, этап остаётся открытым.

Activity recreation восстанавливает draft/экран и подписку. Process recreation
не доверяет прежнему факту окна: заново проверяет boot, stop, grants, срок,
sync и exclusions. Только допустимый recovery восстанавливает прежнюю negative
сессию; overdue обрабатывается до addOverlay. Это не восстановление по onResume.

### 5.3. Clock record и алгоритм-кандидат

Сохранить вместе с sessionId/revision: `bootCount`, anchor UTC и elapsedRealtime,
исходные duration/deadline UTC и monotonic deadline, признак целостности и
известной потери пригодности wall-clock anchor. Все сложения проверять на overflow.

1. В той же загрузке источником остатка служит только monotonic deadline.
   Sleep считается. Смена timezone меняет только отображение.
2. При обработанном wall-clock change внутри загрузки mono deadline не сдвигается.
   Для последующего reboot UTC-представление пересчитывается как
   `nowUtc + (monoDeadline - nowElapsed)` с той же revision, без rearm.
   Anchor/UTC deadline записываются целиком. При невозможности сохранить
   согласованный anchor межзагрузочное восстановление помечается непригодным;
   действующий mono timer в этой загрузке не отменяется самим clock change.
3. После reboot mono предыдущей загрузки не применяется. Проверяются схема,
   полнота, revision, boot marker, источник установки, длина исходного интервала,
   известная clock-invalid отметка и согласованность UTC полей. UTC раньше
   последнего сохранённого anchor, невозможный интервал или противоречивые поля
   исключают восстановление overlay. `nowUtc >= deadlineUtc` → expiry до окна.
4. При полной непротиворечивой записи без установленной clock-проблемы кандидат
   использует исходный UTC deadline и остаток `deadlineUtc-nowUtc`; срок нельзя
   увеличить до полной duration или перенести старый elapsedRealtime буквально.
   После допуска записывается anchor новой загрузки с тем же концом.
5. Это **ограниченная проверка пригодности, не доказательство истинного UTC**.
   Она не обнаруживает все изменения часов, сделанные при выключенном устройстве.
   AUTO_TIME не повышает запись до доказанной. Optional чтение системного
   network-time на33+ может дать дополнительное свидетельство, но не обязательную
   сеть/новое разрешение и не обещание точности; не включать его в первую схему
   без отдельной оценки необходимости.

До реализации этой ветви зафиксировать executable fixtures нормальных двух
reboot, rollback/forward часов, неполного anchor и пропущенного time-change.
Если кандидата недостаточно для принятого RULE-046, технический gate не пройден;
не подменять это произвольным «всегда доверять AUTO_TIME» либо новой boot policy.
Порог расхождения при добавлении другого источника времени сейчас не выбран;
в первой схеме нет выдуманного универсального допуска секунд.

DE snapshot содержит только boot policy/значение, last target/допустимость
восстановления, floor/версию mapping, срок/revision и terminal/clock markers.
Ранний путь проверяет version/целостность и доступность записи; недостающие
данные не становятся старой отрицательной целью по default.
После unlock источником полной актуальной записи становится CE; DE сверяется
по revision. Перед потенциально опасным изменением CE прежний DE restore
сначала инвалидируется, после commit публикуется новый snapshot. Между файлами
нет транзакции: разрыв приводит к запрету старого restore, а не к угадыванию.

## 6. Storage, migration, backup и внешние identities

### 6.1. Хранилище: уточнение2026-10-15

**Рекомендация по порученному выбору — типизированный DataStore с Kotlin
Serialization/JSON.** Пользователь не утвердил прежний SQLiteOpenHelper и поручил
выбрать DataStore, если нет существенных компромиссов; блокирующей потребности в БД
по требованиям BCD не найдено. Это оценка по API, не результат Android-пробы.

| Вариант | Применительно к BCD |
|---|---|
| DataStore + Kotlin Serialization/JSON | Kotlin-модели, небольшой Serializer, без `.proto`/protoc/DAO/SQL; подходит небольшому фиксированному snapshot. Нужны стабильные имена полей, schemaVersion, defaults и явные преобразования несовместимых версий |
| Proto DataStore | Та же атомарность DataStore; компактный бинарный формат и правила эволюции numbered fields/unknown fields. Дополнительные `.proto`, protobuf plugin/protoc и generated types; полезный вариант, но текущие данные BCD не требуют этой инфраструктуры |
| Room | Транзакции/SQL-проверки/миграции; выгоден большим наборам, выборкам и связям. Для BCD пока нет запроса на историю, joins или referential integrity; entities/DAO/code generation не дают необходимой функции |
| SQLiteOpenHelper | Транзакции без ORM, но собственные SQL, mapping и schema management; дороже в сопровождении, чем нужно BCD. Прежний выбор заменён этой оценкой, история остаётся в Git |

Один неизменяемый CE объект `BcdState` содержит связанные настройки, widget
instances, runtime receipt и import marker. Save duration+deadline, конфигурация
widget и завершение импорта выполняются одним `updateData`, а не цепочкой файлов.
Один DataStore instance на файл в одном процессе; копии моделей/коллекций не
изменяются после публикации. Не создавать store на каждый widget ID.

| Часть CE объекта | Данные и существенные ограничения |
|---|---|
| settings | Типизированные опции, timer enabled/duration, boot policy/fixed; revision |
| presets | Набор MAIN/SHARED, индекс; ровно8/4, значение[-75,100]; шаги отдельно |
| widget_instances | provider, appWidgetId, incarnation, step/opacity/Auto, конфигурация подтверждена; уникальность provider+ID |
| control_session | Последняя цель отдельно от текущей сессии; command/session IDs, revision, deadline/anchor, стадия/terminal/result |
| entitlement | Независимые paid evidence/cache, legacy-unknown и promo observation; unknown/error не false |
| migration | Версия схемы/импорта, источник, завершение импорта, отметка сообщения negative, выбранный channel ID |

Импорт — небольшой идемпотентный `DataMigration<BcdState>`: нормализовать оба
Legacy SharedPreferences и записать данные с marker одним обновлением; повтор
после сбоя не затирает уже изменённые настройки. Исходные prefs автоматически
не очищать: generic migration с отсутствием destructive cleanup вместо слепого
применения helper, удаляющего импортированные ключи. В migration нет эффектов света.

DE — отдельный минимальный типизированный snapshot, например второй DataStore
через device-protected context. Общей CE/DE транзакции нет; согласование revision
и запрет старого restore при разрыве сохраняются из5.3. До unlock CE store
не инициализируется. DataStore не доказывает факт окна, причину Stop или clock trust.
Ни Room/SQLite, ни другой serializer не делают эти Android эффекты атомарными.

Backup целого CE файла запрещён: он содержит local/runtime/rights. Механизм
экспорта разрешённой типизированной проекции выбирается при реализации по6.3,
без общего framework backup. Эволюция JSON: добавлять поля с defaults, сохранять
wire names, несовместимые изменения преобразовывать по schemaVersion и fixtures;
неизвестную будущую схему/повреждение не затирать молча defaults. Чтение новых
полей старой версией не равно обещанию безопасного downgrade.

Ограничение обоих DataStore вариантов — запись всего объекта. Сохранять значимые
переходы/квитанции, не каждый observer callback или кадр отображения; проверить
continuous slider без потери принятой семантики. Если реальные размер/нагрузка
покажут существенную проблему, тогда обосновать Room. Зависимости/совместимость
serialization plugin с текущим toolchain проверяются при реализации; сейчас не меняются.

### 6.2. Импорт Legacy

1. На первом допустимом CE startup прочитать оба исходных SharedPreferences
   без удаления/перезаписи. Точные filenames и типы сверить с установленным
   совместимым Legacy fixture, а не только с названием Java constant.
2. Собрать нормализованный snapshot, валидировать поля по отдельности.
   Нераспознаваемое поле получает свой документированный default;
   валидное соседнее не теряется. Не clamp неверный preset в другое число.
3. Перенести main8/shared4/независимые steps, visibility/options, duration и enabled.
   Release duration index0..47 →30*(index+1) минут, default index5→3h.
   Принятый2026-10-15 приоритет enabled: hidden runtime key, если валидный bool;
   иначе checkbox key; иначеfalse. Это8.7; не смешивать с отдельным правилом widget Auto.
4. Widget Auto: explicit per-ID > global >false; step/opacity из named prefs.
   Сопоставить только с реально известными provider instances. Orphan prefs
   не создают widget/действие. Каждому живому instance назначить новую incarnation.
5. Negative presets перенести численно. Previous brightness/before-Auto/sentinel
   сохранить при необходимости только как сведения об импорте; они не доказывают
   active session/deadline. Duration/enabled не превращаются в действующий timer.
6. Сохранить нормализованные данные и completed marker в одной CE-транзакции.
   До её завершения не публиковать половину миграции как успешную. Повтор после
   crash до commit повторяет импорт; после commit не затирает новые изменения.
7. Обновить DE и views без команды света. При первом видимом входе показать
   принятое однократное сообщение negative; подтверждение показа/закрытия хранить
   отдельно. Недоступный UI не считается просмотром сообщения.

Сохранение исходных prefs позволяет исследовать ошибку импорта, но не обещает
возможность APK downgrade со всеми новыми настройками. При ошибке schema/import
не делать destructive reset или автоматическую очистку данных.

Минимальные fixtures: fresh; полный valid Legacy; пропущенные/неверно типизированные
поля; границы и invalid presets/steps; оба enabled ключа и их конфликт; все48
duration indices; sentinel/старый negative; split widget stores; два instances;
orphan/deleted/restored IDs; premium true/false/absent; разные каналы;
crash до/после commit; storage failure; backup с другого устройства.
Fixtures обезличиваются: purchase tokens/секреты/личная конфигурация не коммитятся.

### 6.3. Backup

Приняты принципы backup настроек; конкретный механизм выбирается при реализации.
Рабочий вариант — исключить CE/DE runtime files из cloud/device transfer и
формировать отдельный версионированный переносимый snapshot настроек:
presets/steps/visibility/options, boot policy, timer enabled/duration, first-help
и отметка сообщения миграции. Это проекция подтверждённых данных, а не второй
источник runtime. При сбое экспорта настройки остаются в CE store; успешность создания
backup не заявляется. Сам Android backup не гарантирует захват последней записи.

Не включать runtime/last active target/deadline/операции, grants, выбранный ID
канала, Billing tokens/локальное подтверждение права и действующие widget IDs.
Права после reinstall/переноса запрашиваются через принятый Play restore;
сбой не объявляется подтверждённым отсутствием покупки.

Для сохранения конфигурации виджетов при host restore отдельно экспортировать
неактивные restore records параметров с прежними ID только как ключами сопоставления.
Они не попадают сразу в коллекцию живых instances. Лишь полученный host
onRestored(oldIds,newIds), проверенный provider/новый ID и новый incarnation
публикуют перенесённую конфигурацию. Простое совпадение чисел ID запрещено.
Порядок доставки backup/host callbacks и отсутствие mapping — ранний TEST-030/046/047:
при неполном mapping нет случайного присвоения чужому виджету.
Принципы8.5 приняты; технический путь требует реального host proof.

### 6.4. APK, providers, каналы и права

До подписанного опыта проверить maximum versionCode всех опубликованных и
тестовых tracks и совместимую app-signing identity/lineage. Номер не назначается
по формуле49+1. Upload certificate не заменяет подпись установленного APK.
Приватные ключи/пароли не запрашиваются в документы.

Сохранить provider component names Legacy:
`.widget.WidgetBrightnessVal`, `.widget.WidgetNotification`,
`.widget.WidgetPlusMinusHorizontal`, `.widget.WidgetPlusMinusVertical`.
Проверить compatibility entry points прежних configure activities и
`.ui.MainActivity` (при необходимости activity-alias к новой Activity).
Это сохраняет связь host/старых shortcuts, а не требует старую Java реализацию.

Каждое новое widget действие: explicit destination + identity по
provider/ID/incarnation/action, immutable; параметры брать из актуального
подтверждённого store после проверки живого instance, а не stale extras step.
Delete делает incarnation недействительным и отменяет PIs; повтор delete безопасен.
onRestored выдаёт новые actions. При MY_PACKAGE_REPLACED перерисовать все живые
widgets и заменить старые controls/notification actions без применения света.
Старый `.service.DimmerService` PendingIntent требует явного compatibility
решения: неподтверждённое старое действие не исполняется как новая команда;
entry point может обновить controls. Проверить период до первого host refresh,
а не считать сохранённое имя provider достаточным доказательством upgrade.

Канал: fresh installation → один стабильный ID, initial HIGH без sound/vibration.
Upgrade → перечислить старые ID и сохранить выбранный existing ID как стабильный,
не создавать новый HIGH вместо blocked. При нескольких каналах действует
принятый принцип сохранения ограничений8.1; точный алгоритм выбора пока
не утверждён и проверяется при upgrade. Автоматической очистки старых каналов нет.
Повторный startup/toggle не увеличивает число каналов. Пользовательские настройки
всего выбранного канала не переписываются; прежние дубликаты не объявляются удалёнными.

Права: Play adapter хранит premium_upgrade, текущую PURCHASED покупку и
подтверждение обработки; PENDING не выдаёт право, non-consumable не consume.
Проверка purchase provenance/подлинности и acknowledgement recovery обязательны;
TODO validator=true из Legacy не переносится. Первый вариант — локальная проверка
доступных purchase данных и Play queries без нового backend; уровень доказательства
и неоднозначные результаты фиксировать в TEST-053/054, не заявлять server validation.
Legacy IS_PREMIUM отделён от paid evidence; его доступ предложен в8.2.
Game grant — отдельное основание; удаление игры не стирает paid.

Store/Ads создаются централизованно одним Play/AdMob profile. Небольшие контракты
offer/purchase/restore/entitlement и ad placement позволяют позднее заменить
адаптер. Subscription capability unavailable, без предложения/SDK/backend
подписки. SDK family/version проверить перед будущей интеграцией; текущий catalog
не меняется. Право/consent учитываются до Ads init; при unknown доступе не
спешить инициализировать рекламу. Offline/SDK failure не задерживают свет.

Изменение slider/таймера не должно непрерывно перехватывать фокус и зачитывать
каждый кадр. При expiry editor/help остаётся открытым, обновляется состояние.
Compose accessibility checks34+ дополняют ручной TalkBack26/37 и host проверки.

Предлагаемая форма: field errors под полем; отказ света/доступа — постоянный
блок в текущем BCD экране, убираемый пользователем либо новым относящимся
результатом. Действие «Открыть настройки Android» доступно только из UI.
Share launch failure — Snackbar с сообщением принятого смысла, доступный
screenreader и с системным accessibility timeout; отмена Share без сообщения.
Сохранение настроек подтверждают обновлённые подписи, без лишнего сообщения
«яркость применена». Однократное сообщение negative — dismissible блок на Main.
Эти формы приняты2026-10-15 как UX-направление8.8; детали можно корректировать
после UI/accessibility проверки, сохраняя смысл сообщений и доступность действий.

## 8. Предложения и результаты согласования2026-10-15

Номера локальны этому плану, не новые DEC/Q/TEST ID. Исходные шесть частей
ниже сохраняют контекст предложений; текущий статус указан перед каждым случаем.
Принятие не является выполненным тестом и не пересматривает группы1–7.

### 8.1. Несколько противоречащих старых каналов

**Предварительно принят принцип сохранения пользовательских ограничений.**
Blocked/minimum importance/newest tie-breaker ниже не утверждены как алгоритм;
выбор проверяется на реальном upgrade, без блокировки независимой работы.

1. **Предмет/статус:** новое правило выбора existing channel при upgrade.
2. **Legacy/основание:** timestamp ID менялся ради настройки importance;
   preferred ID не сохранён. E14/E15 и история91e4fbf7; снимок Honor показывает
   дубликаты, но не последнюю выбранную пользователем конфигурацию.
3. **Предложение/почему:** один канал переиспользовать целиком; при нескольких
   предпочесть blocked, иначе наименьшую importance, при равенстве более новый
   timestamp ID. Не merge, не delete и не новый HIGH. Это консервативный выбор,
   который может выбрать старый ограниченный канал вместо желаемого нового;
   показать путь к настройкам ОС. По исходникам устранить неоднозначность нельзя.
4. **Экран/условия:** после upgrade Settings BCD → Уведомления; старый LOW и
   новый HIGH, оба с собственными системными параметрами.
5. **События:** BCD перечисляет каналы, выбирает LOW и сохраняет его ID;
   пользователь при необходимости открывает системные настройки этого канала.
6. **Результат:** BCD не повышает важность за пользователя и не размножает каналы.
   Прочие старые каналы остаются. Свет/срок не меняются; существующий expiry
   обрабатывается своим событием независимо от чтения Settings.

### 8.2. Legacy Premium=true без происхождения

**Принято:** сохранить локальный доступ неизвестного происхождения отдельно от
подтверждённой покупки. DEC-021/RULE-036–037; TEST-046/054/055.

1. **Предмет/статус:** новое правило локального доступа при совместимом upgrade,
   не изменение товара/цены/политики прежних оплаченных прав.
2. **Legacy/основание:** один IS_PREMIUM писали purchase и hidden help taps;
   назначение taps — тестирование/друзья. E30/E35, история92da49f8. По bool нельзя
   отличить покупателя от получателя старого ручного доступа.
3. **Предложение/почему:** сохранить прежний локальный доступ при true как
   `legacy origin unknown`, отдельно от доказанной покупки, без календарного
   срока отключения. Unknown/error/пустой query другого аккаунта его не стирают.
   Если позднее получено относящееся подтверждение покупки — сохранить paid
   evidence; действительный установленный отзыв учитывать только по его данным.
   Без возможности установить происхождение автоматическое лишение недопустимо;
   следствие — часть прежних ручных grants тоже продолжит работать на этой установке.
4. **Экран/условия:** обновлённая BCD, старое true, сети/ответа Play нет;
   Settings → Premium и доступный редактор preset.
5. **События:** BCD импортирует локальный доступ; пользователь открывает редактор,
   затем может нажать «Восстановить покупки». BCD различает подтверждение и ошибку.
6. **Результат:** прежний доступ не пропадает и новая оплата не навязывается;
   при ошибке видно «Не удалось проверить покупку. Прежний доступ сохранён».
   Нет ложного «Покупка восстановлена». Старый bool не экспортируется как новая
   оплаченная лицензия на другой телефон; там действует Play restore. Свет не меняется.

### 8.3. Внешний вход при открытом редакторе

**Принято для навигационного входа:** открытый editor/draft сохраняются.
Командные действия widgets/notification продолжают выполнять ранее принятые
команды; их нельзя превращать в одно открытие editor. DEC-007/RULE-013/TEST-019.

1. **Предмет/статус:** ещё не выбранная навигация/сохранность draft.
2. **Legacy/основание:** отдельный editor и singleTask Main; E10/E13 и история
   dcc86019 объясняют одну панель, но не доказывают сохранение editor task stack.
3. **Предложение/почему:** одна MainActivity с внутренними Compose routes;
   повторное открытие BCD поднимает текущий экран, не сбрасывая открытый editor
   и не сохраняя draft. Это не выбор архитектуры архивного prototype.
4. **Экран/условия:** main preset25, пользователь длинным tap открыл editor и
   ввёл75, Save ещё не нажат; затем Home → значок BCD/value widget/content notice.
5. **События:** ОС доставляет внешний вход существующей Activity; BCD оставляет
   editor75. Пользователь сам нажимает Save либо Cancel/Back.
6. **Результат:** Save→кнопка75; Cancel/Back→кнопка25 на Main. Сам повторный вход
   не меняет свет. Если актуальный timer истёк, обработка снимает overlay/запрашивает
   Auto, но editor и draft остаются; последующий Save не возвращает прежнее dim.

### 8.4. Первый help

**Принято как UX-направление:** однократный Help; детали корректируются после
UI/accessibility проверки без повторного согласования каждой внутренней детали.

1. **Предмет/статус:** новый макет уже принятого первого входа в help.
2. **Legacy/основание:** first flag записывался перед help,6 активных страниц;
   E12/E35 и история прокрутки объясняют назначение первого входа и доступного выхода.
3. **Предложение/почему:** первый видимый вход сразу показывает одну прокручиваемую
   Help поверх внутреннего Main route; Back возвращает Main, повторно автоматически
   не открывать. Отметить первый фактический показ, а не полноту прочтения.
4. **Экран/условия:** fresh install, первый Launcher-вход; специальных доступов нет.
5. **События:** BCD показывает Help, пользователь читает или сразу закрывает Back,
   позднее открывает BCD снова. BCD учитывает первый показ, не полноту прочтения.
6. **Результат:** после Back Main доступен, повторного автоматического help нет;
   ручной вход остаётся. Ни один показ не выполняет свет/таймер и не требует grant.

### 8.5. Переносимые настройки и данные конкретного устройства

**Приняты принципы:** настройки переносятся; сессия/deadline/grants/устройство-
зависимые доказательства права — нет. Механизм не заморожен; выбирается при реализации.

1. **Предмет/статус:** ещё не выбранное содержимое cloud/device backup.
2. **Legacy/основание:** allowBackup=true, defaults/named widget prefs и общий
   runtime/cache не разделены; новый проект содержит только placeholders.
   Техническая оценка§6 не утверждает готовую политику переноса.
3. **Предложение/почему:** переносить настройки/числовые presets и безопасные
   отметки показа. Не оживлять сессию/срок/разрешения/локальное paid evidence.
   Widget config публиковать лишь по настоящему host mapping, не совпадению ID.
4. **Экран/условия:** пользователь восстановил данные BCD на другом телефоне,
   открывает Main/Settings; сохранены preset−50 и duration3h.
5. **События:** BCD импортирует переносимые настройки, читает новую ОС/доступы;
   Play restore отдельно проверяет покупку; host при наличии передаёт mapping IDs.
6. **Результат:** кнопка−50 и3h сохранены, старое затемнение/отсчёт не включены,
   новые grants не считаются выданными. Совместимый upgrade на прежней установке
   остаётся другим путём с сохранением локального права по8.2.

### 8.6. Labels без постоянно работающего сервиса при Auto/manual

**Не принято окончательно.** Нужна небольшая техническая проверка влияния FGS
lifetime на привычное поведение widgets/notification; snapshot labels ниже
остаются кандидатом. Зависимые решения ожидают результата, независимые этапы идут.

1. **Предмет/статус:** предлагаемое честное представление пассивных surfaces;
   это не доказанная постоянная синхронизация после смерти процесса.
2. **Legacy/основание:** labels обновлялись из service/observers, но saved numeric
   и Auto могли расходиться; E07/E14/E17. Безусловная вечная работа не доказана.
3. **Предложение/почему:** вне negative не держать отдельный FGS ради наблюдения.
   Value/controls widgets и обычное controls notification показывают «Последняя
   проверка:25%/Авто» как snapshot; обновляются при доступных событиях/входах и
   после команды. Main всегда перечитывает ОС; step всегда берёт актуальный raw,
   а не snapshot. Пока runtime наблюдает, можно показывать подтверждённое состояние.
4. **Экран/условия:** Auto/manual без negative; процесс BCD уже не работает;
   пользователь поменял яркость средствами ОС и смотрит старый value widget.
5. **События:** widget не выдумывает получение нового raw; пользователь открывает
   BCD либо нажимает доступный control, BCD читает текущее состояние и обновляет views.
6. **Результат:** последний снимок не выдан за постоянно актуальное значение;
   новая команда использует актуальные данные. Принятие такого текста/ограничения
   требуется отдельно; при непринятии исследовать допустимый способ наблюдения,
   не объявлять RULE-007/019 выполненными при заведомо устаревшей подписи.

### 8.7. Конфликт двух старых timer enabled ключей

**Принято:** приоритет валидного фактически используемого service ключа,
затем checkbox, затем defaultoff; импорт сам не создаёт сессию/deadline.

1. **Предмет/статус:** новое детерминированное правило импорта конфликта.
2. **Legacy/основание:** UI checkbox listener записывает hidden enabled, service
   читает hidden. E15/E23; SharedPreferencesChangeListener и setDimmerDeactivationAlarm
   перечитаны. Причина возможного конфликта конкретных установок не установлена.
3. **Предложение/почему:** валидный hidden bool приоритетен, при его отсутствии
   валидный checkbox, иначе defaultoff. Это выбирает рабочее значение service,
   но при конфликте может отличаться от прежней видимой галочки.
4. **Экран/условия:** после upgrade Settings → Таймер; fixture checkbox=true,
   hidden=false, сохранённая release duration index5.
5. **События:** BCD импортирует enabled=false и3h в одну транзакцию; пользователь
   видит выключенный таймер и может явно включить его для последующих действий.
6. **Результат:** при самом upgrade нет отсчёта/изменения света. Обратный конфликт
   импортирует enabled=true, но также не создаёт старую negative сессию или deadline.

### 8.8. Форма ошибок и сообщения миграции

**Принято как UX-направление.** Смысл ошибок/результатов сохраняется; визуальные
детали можно корректировать по UI/accessibility проверке.

1. **Предмет/статус:** выбор способа показа уже принятых сообщений; ниже отдельные
   варианты по месту ошибки, без изменения их смысла или исходов операции.
2. **Legacy/основание:** E10/E25/E36 и обзор группы6 показывают field validation,
   permission объяснения и Share; комментарий editor предупреждает о перекрытии Ok.
   Snackbar новой версии ранее не принят.
3. **Предложение/почему:** ошибка ввода под полем; отказ света/доступа постоянным
   блоком в BCD до закрытия пользователем/нового относящегося результата;
   Share launch failure Snackbar с accessibility timeout. Однократное сообщение
   об изменении силы negative — закрываемый блок Main, без автоматического применения.
4. **Экран/условия:** А: editor preset25, ввод101. Б: Main, нет нужного доступа
   для выбранной команды. В: Main → Share, запуск chooser не удался со стороны BCD.
   Г: первый видимый Main после импорта старого negative preset.
5. **События:** А пользователь нажимает Save; Б выбирает команду и получает отказ;
   В BCD получает ошибку запуска; Г BCD показывает сообщение и пользователь закрывает его.
6. **Результат:** А editor сохраняет введённое101, saved25 и доступные Cancel/Save.
   Б Main остаётся с объяснением и кнопкой настроек; поздний grant ничего не применяет.
   В Main доступен, Snackbar говорит «Не удалось открыть выбор приложения для отправки ссылки»;
   обычная отмена Share без сообщения. Г preset сохранён численно, после закрытия
   блок не навязывается повторно. Сообщения сами не меняют свет или deadline.

## Первичные источники для технических кандидатов

Android источники сверены2026-10-14, storage повторно2026-10-15. Источники
подтверждают API/ограничения, а не работающее BCD. Выбор DataStore — рекомендация
по порученной оценке; CE/DE/backup механизмы и anchor подлежат ранним проверкам.
Остальная опора — техническая оценка/E/P выше.

- [FGS background starts](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start): основания пользовательского/boot входа и ограничение SAW наtarget35+.
- [Special use](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use): тип/subtype и необходимость Play review.
- [User stopping](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping): отсутствиеcallback, сохранениеalarms/jobs, ApplicationExitInfo.
- [Direct Boot](https://developer.android.com/privacy-and-security/direct-boot): CE/DE и событие первого unlock; отдельный startup без личных CE данных.
- [SystemClock](https://developer.android.com/reference/android/os/SystemClock): elapsedRealtime и границы network-time API33+.
- [DataStore](https://developer.android.com/topic/libraries/architecture/datastore): типизированные JSON/Proto объекты, singleton, immutable data и ограничения небольших datasets.
- [DataStore updateData contract](https://github.com/androidx/androidx/blob/androidx-main/datastore/datastore-core/src/commonMain/kotlin/androidx/datastore/core/DataStore.kt): атомарное обновление одного объекта; не общая транзакция CE/DE или ОС.
- [DataMigration contract](https://github.com/androidx/androidx/blob/androidx-main/datastore/datastore-core/src/commonMain/kotlin/androidx/datastore/core/DataMigration.kt): идемпотентность и повтор при сбоях.
- [Proto evolution](https://protobuf.dev/programming-guides/proto3/#updating): numbered fields и совместимость изменений.
- [Room](https://developer.android.com/training/data-storage/room): SQL-проверки и migrations; для relational данных предпочтительнее прямого SQLite API.
- [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile): файловая публикация с обязательной собственной сериализацией доступа.
- [Notification channels](https://developer.android.com/develop/ui/compose/notifications/channels): сохранение existing ID и уважение пользовательских параметров.
