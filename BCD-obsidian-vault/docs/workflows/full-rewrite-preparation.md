# Подготовка эксперимента полного переписывания BCD

Создано 2026-10-04; обновлено 2026-10-06. Статус: согласование требований перед планированием.

Этот документ сохраняет ответы пользователя и предложения для обсуждения.
Он не является разрешением начать реализацию, готовым планом или подтверждением
работоспособности механизмов. Предложения ниже не становятся требованиями по
отсутствию ответа. Коммерческие DEC/RULE/SCN/TEST согласованно обновлены после
ответов 2026-10-05; reboot-контракт ещё уточняется. PENDING_USER у DEC-013 не
следует трактовать как полное отсутствие ответа пользователя.

См. [спецификацию](../specification/product-specification.md),
[журнал решений](../specification/behavior-decisions.md),
[прогресс](../specification/workflow-progress.md) и
[глоссарий](../specification/glossary.md).

## Уже заданные пользователем границы

- Полное переписывание в новом Android-проекте на Kotlin с архитектурой MVVM.
- Использовать недавно модернизированный стек. Дополнительное массовое обновление
  не требуется; замена устаревшей технологии требует конкретного обоснования.
- Подготовить и согласовать требования и план перед автономным выполнением.
- Сохранить возможность общего возврата всех папок и независимых репозиториев.
- Вопросы задавать обычным текстом чата, без исчезающей формы ответа.
- Обращать внимание пользователя на проблемы и предлагать улучшения.

## Ответ по Q-001: поведение после перезагрузки

Пользователь описал противоречивые жалобы: отсутствие восстановления желаемой
яркости; восстановление слишком низкой яркости при выходе на свет; повторение
полной потери видимости экрана после reboot, не позволяющее выйти из цикла.
Предотвращение последнего случая — обязательная цель новой версии.

Пользователь предложил настройку политики после reboot:

- Auto по умолчанию.
- Восстановление ранее установленной пользователем яркости с ограничением снизу
  и предупреждением о возможной плохой видимости при ярком внешнем освещении.
- Дополнительные варианты можно предложить для обсуждения.

Точная величина нижнего ограничения, дополнительный запас над ним и семантика
отрицательного последнего значения пока не определены. Исторический floor5 BCD
не означает физически безопасную яркость любого OEM-устройства. Тестирование
значений ниже защитного порога и индивидуальная калибровка не разрешены.

Уточнение пользователя 2026-10-05: предпочтителен опциональный возврат overlay,
включённый по умолчанию, если нет существенного усложнения или проблем. При
сильном усложнении пользователь предложил постоянный возврат с возможностью
легко изменить политику в коде. Это условное пожелание; обнаруженные риски нужно
представить пользователю до окончательного выбора. Оно не означает, что Auto
должен запускаться одновременно с прежним затемнением. Общий default Auto из
предыдущего ответа сохраняется, пока пользователь явно не изменит его.

Окончательный выбор default переключателя 2026-10-05: пользователь согласовал
выключенное восстановление overlay в режиме «Последний режим BCD». Восстановление
остаётся опциональным. Учтены противоположные жалобы, в том числе чтение ночью
после reboot; default можно пересмотреть по обратной связи. Возможность изменения
default не должна молча перезаписывать уже сохранённый явный выбор пользователя.

2026-10-06 пользователь подтвердил добавление третьего режима «Заданная яркость».
Точное допустимое значение, default и нижнее ограничение ещё не выбраны.

Опциональность имеет небольшую стоимость UI/настроек. Основная сложность —
сам механизм boot restore: background/FGS/Direct Boot, grants, испорченные значения,
exclusions, timer, повторные события и аварийное снятие затемнения. Эти задачи
остаются и при постоянном возврате. Существующая защита на screen-событиях не
работает, если приложение не получает события; обычный in-process timer не
доказывает восстановление после смерти процесса.

Предложения агента, ожидающие согласования:

- Показывать настройку «Восстанавливать дополнительное затемнение» только в
  применимом режиме. Auto default и выключенный default восстановления overlay
  в «Последнем режиме BCD» согласованы; конкретное оформление настройки ещё нет.
- Пользователь принял опциональный overlay после первой разблокировки; раннюю
  коррекцию системной яркости рассматривать отдельно. Исходное окончание таймера
  сохраняется через reboot. Clock/recovery требуют технического решения и проверок.
  Это не принятие новой calibration.
- Для подтверждённого режима «Заданная яркость» предложено отдельное положительное
  значение выше принятого ограничения. Диапазон и умеренное значение по умолчанию
  выбрать после проверки, а не объявлять процент универсально безопасным.
- Отделить последнюю пользовательскую команду BCD от наблюдаемого значения ОС:
  внешнее изменение и мгновенная выборка Auto не должны молча менять смысл
  «восстановить ранее выбранное».
- Для Auto определить обработку неподдерживаемого режима или отказа записи.
  Предлагаемый fallback — проверенное положительное значение без overlay;
  точное правило требует решения и проверки.
- Не переигрывать старую команду затемнения при обычном открытии приложения или
  повторной доставке события загрузки. Таймер через reboot сохраняет исходное окончание; способ хранения определить в плане.

До принятия технического решения проверить Direct Boot, доступность сохранённой
политики до первой разблокировки, разрешение WRITE_SETTINGS, повторные события,
остановку приложения и ограничения фонового запуска на API26–37. Boot receiver
не гарантирует исполнение с самого начала загрузки. Защита должна охватывать
обычные команды, повреждённые/мигрированные настройки и восстановление, а не
опираться только на последующий reboot callback. Абсолютная гарантия для любого
OEM, внешних записей яркости и отсутствующих разрешений не доказана.

### Пояснения для следующего ответа пользователя —2026-10-06

«Раньше» означает после загрузки Android до первой разблокировки, когда виден
экран ввода PIN/пароля, а не во время логотипа/анимации загрузки. Direct Boot
требует отдельного доступного до unlock хранения и компонентов; разрешённость
запуска и показа overlay проверяется отдельно. «После первой разблокировки» —
после первого успешного снятия блокировки в этой загрузке, когда ОС разрешит
обработку события и проверены grants/состояние/таймер. Это не ожидание открытия
BCD и не обещание фиксированной задержки в секундах. Повторная разблокировка
не должна заново запускать срок/восстанавливать истёкшее затемнение. Если защиты
экрана нет, отдельного ожидания ввода PIN нет. Overlay может не покрывать
защищённые окна; выбор момента не даёт гарантии работы на экране блокировки.

Рекомендация агента: опциональный overlay восстанавливать после первой
разблокировки. Раннюю коррекцию системной яркости рассматривать отдельно,
чтобы не переносить риск неразличимого экрана на ввод PIN. В последующем ответе 2026-10-06 пользователь принял этот момент; RULE-041.

В Legacy есть «Отключать диммер по таймеру» и «Отключать диммер через»:
`BrightnessControlDimmer/src/main/res/xml/preferences.xml:16–27`,
`values-ru/strings.xml:118–123`. Default off, длительность 3h; в production
интервалы 30min. Активный alarm назначается заново от текущей negative команды
в `service/DimmerService.java:811–839`, используется ELAPSED_REALTIME в
`utils/Utils.java:716–738`. Boot-команда устанавливает Auto:
`service/DimmerService.java:609–617`. Отдельной пользовательской настройки
продолжения активного отсчёта через reboot в просмотренном коде нет; сохранение
старого deadline не найдено. Это согласуется с LB-029/LB-033/E21.

Разумные варианты при разрешённом восстановлении overlay:

- Сохранить исходный момент окончания, считая время выключения/загрузки/ожидания
  unlock. Если срок уже прошёл, overlay не возвращать. Рекомендация агента:
  не продлевает затемнение из-за reboot; изменение часов/неизвестность срока
  требует отдельной защитной политики и проверки.
- Сохранить остаток и продолжить его при возврате overlay, не считая перезагрузку
  и ожидание. Более длительная сессия, нужна однозначная политика сохранения
  остатка при внезапном отключении питания.
- При восстановлении начать полный заданный интервал заново. Проще объяснить,
  но каждая перезагрузка продлевает затемнение; агент не рекомендует как default.
- Завершить сессию с активным таймером при reboot: overlay не возвращать,
  сохранить пользовательские настройки для следующего ручного включения.

Если выбран Auto/«Заданная яркость» или восстановление overlay выключено,
старый таймер не должен позже переиграть новую политику загрузки. Не предлагается
сразу вводить отдельную настройку для всех четырёх вариантов; требуется выбрать
общую семантику. В последующем ответе 2026-10-06 пользователь принял первый вариант; RULE-042.

## Ответ по Q-002: монетизация и магазины

Пользователь выбрал сохранение существующих способов монетизации: Premium,
реклама и промо-доступ через установленную игру, с учётом возможностей магазина.
Также требуется архитектурно и в дизайне рассмотреть подписку за дополнительные
функции. Конкретные функции, продукты, цены и запуск подписки не утверждены.

Требуется удобный выбор платёжных и рекламных провайдеров и активных способов
монетизации для разных магазинов с изменениями в ограниченном числе точек.
Уточнение пользователя 2026-10-05: все ранее оплаченные Premium-права обязательно
сохраняются и восстанавливаются. Подписка только для будущих новых функций;
production-продажи подписки сейчас не поручены. Первый выпуск — Google Play
и существующий AdMob. Huawei AppGallery и RuStore — вероятные последующие магазины.
Присутствие Amazon-кода Legacy не расширяет этот объём. Перенос между магазинами
и необходимость backend остаются отдельными решениями.

Пункт «Восстановить покупки», Google Play Billing и AdMob подтверждены исходниками.
Исследование провайдеров, региональные ограничения, источники и рекомендации
сохранены в [отдельном обзоре](monetization-provider-research.md).

Предлагаемый подход, пока не утверждённая архитектура:

- Общая модель прав: какие возможности доступны, по какому основанию и на какой
  срок. Отдельно различать бессрочную покупку, подписку и промо-доступ.
- Интерфейсы платёжного и рекламного провайдеров; адаптеры изолируют конкретные
  SDK. UI и логика яркости получают общие состояния, без проверок магазина
  во множестве экранов. Это сочетание адаптеров, стратегии и внедрения зависимостей.
- Профиль магазина задаёт разрешённые предложения, провайдеров, ссылки и прочие
  параметры. Product flavor — вариант сборки; build type — debug/release.
  В APK включаются зависимости и manifest только необходимых провайдеров.
- Feature flags — переключатели доступности уже предусмотренных возможностей.
  Они не добавляют отсутствующий SDK и не подтверждают факт оплаченной покупки.
  Удалённые переключатели необязательны и не должны управлять защитой яркости.
- Многоподульность рассмотреть прежде всего для изоляции SDK и общей модели прав.
  Не создавать отдельный модуль для каждого интерфейса без пользы.
- Неподдерживаемый способ покупки скрывать или объяснять его недоступность.
  Состояние проверки покупки «неизвестно/временно недоступно» отличать от «нет права».

Сохранение прежнего бессрочного Premium с прежними возможностями и подписка для
будущих новых функций теперь явно подтверждены пользователем. Для первой версии
рекомендуются реальный общий контракт прав и доступных предложений, недоступная
subscription capability в production и test-only fake-состояния; полная интеграция
подписки будет зависеть от будущего продукта и backend-решения.

До исполнения плана проверить active Legacy gates, SKU и restore flows по каждому
существующему магазину; будущие SDK и правила конкретных магазинов; подписи,
applicationId и versionCode; проверку покупок, возвраты, истечение подписок,
offline-режим и тестовые окружения. Облачная проверка покупок и перенос прав между
магазинами могут потребовать backend — отдельную серверную систему. Её наличие,
разработка и эксплуатация не подразумеваются и требуют определения границ задачи.
Сохранение рекламы не означает автоматического принятия всех старых SDK
аналитики или Crashlytics.

## Ближайшие уточнения

1. Уточнить параметры заданной яркости, нижнее ограничение, момент применения
   системной яркости и отказ/clock/recovery. Default overlay, третий режим, overlay
   после первой разблокировки и сохранение окончания timer через reboot приняты.
2. Перед проверками магазина/выпуском при необходимости уточнить доступность
   продаж и рекламы действующих Play/AdMob аккаунтов. Это операционная проверка,
   а не обязательное входное условие архитектуры или плана. Под статусом понимаются
   известные сообщения кабинета о доступности/ограничении продаж или рекламы.
   Страна и статус могут помочь оценить региональные ограничения; передавать их
   сейчас не требуется. Credentials, номера счетов и личные документы не нужны.
3. Детальную подписку и межмагазинный перенос оставить будущими решениями;
   не считать их согласованной интеграцией первой версии.

Q-002 закрыт; коммерческие DEC, RULE-036–RULE-040, SCN-044–SCN-050 и
TEST-053–TEST-059 согласованы с глоссарием/прогрессом. После уточнения Q-001
обновить reboot-контракт, согласовать остальные изменения и исключения Legacy,
подготовить план MVVM с проверками. Реализуемость раннего восстановления экрана
должна быть одним из первых проверяемых этапов будущего плана.

## Архив и продолжение работы

Согласование можно продолжать в текущем чате. Решения сохранять в документах.
Перед длительной реализацией новый чат может читать зафиксированные документы
и явное поручение на выполнение; переход не является обязательным.

До первой правки реализации: завершить подготовительные документы и коммиты,
сохранить несвязанные локальные файлы, записать ветки/полные SHA/status всех
репозиториев, поставить общую контрольную метку, остановить процессы записи,
создать и проверить файловый архив вне копируемого дерева. Затем создать
экспериментальные ветки нового приложения и материалов; Legacy оставить для
чтения. О готовности к архивированию сообщить пользователю. Реализацию не начинать
до подтверждения проверенного архива. Откат файлов не возвращает состояние
телефона, эмулятора, магазина или серверов.
